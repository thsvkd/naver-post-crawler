# 핸드오프 — 자격증명 저장과 앱 제거 정책 (레포 간 재사용)

이 문서는 **다른 레포의 에이전트가 그대로 적용할 수 있게** 쓴 정책 핸드오프다.
이 레포(naver-post-crawler)에서 내린 결론을 일반화한 것이며, 레포별로 다시 결정해야 하는
항목은 「레포별 결정」으로 표시했다.

대상: 데스크톱 앱(Windows/macOS)을 설치기로 배포하고, 사용자 자격증명(세션 쿠키·토큰·API 키)을
로컬에 보관하는 프로젝트.

---

## 1. 출발점이 된 잘못된 전제

"설치형으로 바꿨는데 제거해도 파일이 남는다 → 제거 로직을 만들어야 한다."

**이 전제는 틀렸다.** 조사 결과 macOS에서 데이터가 남는 것 자체는 정상이다.

- Apple의 모델에서 `.app`은 자기완결적 번들이고 **휴지통에 넣는 게 제거**다.
  HIG에 별도 언인스톨러라는 개념이 없다.
- `~/Library/Preferences`, `Application Support`, `Caches`에 남는 것은 버그가 아니라
  의도된 동작이다. 재설치 시 설정이 복원되는 게 사용자 이득이라는 논리다.
- 언인스톨러를 제공하는 앱은 기준이 명확하다: **번들 밖에 무언가를 설치했을 때**
  (LaunchDaemon/Agent, 권한 있는 헬퍼, 시스템 확장, 네트워크 필터, 커널 확장).
  Docker Desktop·Zoom·백신·VPN이 제거 도구를 주는 이유가 이것이다.
- `.pkg`로 배포하면 Apple이 제거 메커니즘을 **전혀 제공하지 않는다**(영수증만 남긴다).
  그래서 pkg 배포 앱은 관행적으로 제거 도구를 동봉하는 편이다.

따라서 **"제거 시 데이터 삭제"를 목표로 잡으면 안 된다.** 그건 macOS 관행에 역행하고,
Windows에서도 오삭제 위험만 늘린다.

## 2. 진짜 문제와 진짜 해법

문제를 다시 정의하면 이렇다.

> 남는 데이터가 문제가 아니라, **남는 것이 평문 자격증명**인 것이 문제다.

그러면 해법은 언인스톨러가 아니라 **애초에 평문으로 두지 않는 것**이다.
자격증명을 OS 보관소로 옮기면 세 가지가 한 번에 해결된다.

1. 제거와 무관하게 **평소에도** 디스크에 평문 자격증명이 없다.
2. 휴지통에 드래그해도 남는 건 무해한 설정뿐이다.
3. 남은 보관소 항목은 암호화돼 있고, 사용자가 OS UI에서 직접 확인·삭제할 수 있다.

| OS | 보관소 | 사용자 확인 경로 |
|---|---|---|
| macOS | 키체인 (Security 프레임워크) | 키체인 접근.app |
| Windows | 자격 증명 관리자 (Credential Manager) | 제어판 → 자격 증명 관리자 |
| Linux | Secret Service (libsecret) | 배포판별 |

Python이면 `keyring`이 세 백엔드를 모두 덮는다. macOS·Windows 백엔드는 순수 파이썬 + ctypes라
번들링 위험이 낮다.

## 3. 구현 지침

### 3.1 저장소 seam을 먼저 확인한다

`save_*` / `load_*` 함수 한 쌍이 유일한 진입점인지 확인하고, **시그니처를 유지한 채 내부만
교체**한다. 호출부가 흩어져 있으면 먼저 seam으로 모으는 리팩터링을 별도 커밋으로 한다.

```
save_credential(value)  →  OS 보관소 기록 (파일 기록 없음)
load_credential()       →  보관소 조회, 없으면 None
delete_credential()     →  신설. 보관소 항목 제거 (없어도 성공)
```

### 3.2 백엔드는 반드시 명시 지정한다

`keyring`의 엔트리포인트 자동 탐색에 의존하지 말 것. 번들(PyInstaller / flet build /
Briefcase 등)에는 dist-info가 없을 수 있고, 그러면 탐색이 **조용히 빈 백엔드를 고른다**.
개발 환경에서는 통과하고 배포본에서만 죽는 전형적 함정이다.

```python
if sys.platform == "darwin":
    from keyring.backends import macOS
    keyring.set_keyring(macOS.Keyring())
elif sys.platform == "win32":
    from keyring.backends import Windows
    keyring.set_keyring(Windows.WinVaultKeyring())
```

### 3.3 Windows 크기 한도를 설계에 반영한다

Windows 자격 증명 관리자의 blob 한도는 **2560바이트**이고 UTF-16로 저장되므로 실질 절반이다.
쿠키 헤더 전체나 긴 JSON을 통째로 넣으면 한도를 넘을 수 있고, 넘으면 조용히 실패해
**"로그인은 되는데 저장이 안 되는"** 증상이 된다.

- 저장 전에 길이를 검사해 명확한 오류로 처리한다.
- 실측으로 실제 길이를 확인한다. 넘으면 저장 범위를 좁힌다(필요한 항목만 화이트리스트).

### 3.4 기존 평문 파일 이관

**시점은 "설치 시"가 아니라 "앱 시작 시"다.** OTA 업데이트는 새 설치가 아니어서, 설치 시점에만
걸면 기존 사용자 대부분이 누락된다.

```
시작 시:
  평문 파일 없음        → 아무 일도 하지 않는다 (멱등)
  보관소에 이미 값 있음 → 평문으로 덮어쓰지 않는다 (최신 값 보호)
  그 외                 → 보관소에 기록 → 평문 파일 삭제
```

> **레포별 결정.** 보관소 기록이 실패했을 때 평문 파일을 지울 것인가?
> 지우면 사용자는 재로그인해야 하지만 노출은 확실히 사라진다. 남기면 목적이 달성되지 않는다.
> **재취득 가능한 자격증명(세션 쿠키 등)이면 지우는 쪽을 권한다.**
> 재취득이 어려운 값(사용자가 손으로 발급받은 API 키 등)이면 남기고 경고하는 쪽이 맞다.

### 3.5 제거 시 보관소 항목 정리

- **Windows**: 설치기가 제거 훅을 제공하면 거기서 보관소 항목을 지운다.
  Velopack이면 앱이 `--veloapp-uninstall`로 실행된다.
  - 지우는 대상은 **고정된 항목 이름 하나**여야 한다. 데이터 *폴더* 삭제로 확장하지 말 것 —
    네이티브 훅이 경로를 알아야 해서 하드코딩이 되고, 틀리면 엉뚱한 폴더를 지운다.
  - `install` / `updated` / `obsolete` 훅에서는 **지우면 안 된다**. 매 업데이트마다 로그아웃된다.
  - 항목이 없어도 **성공 코드로 종료**해야 한다. 실패하면 설치기가
    "설치가 부분적으로 성공했습니다"를 띄운다.
- **macOS**: 제거 훅이 존재하지 않는다. 키체인 항목은 남는다. **문서로 안내한다.**
  앱 내 "제거" 버튼을 만드는 것은 권하지 않는다 — Apple 모델에 없는 UI이고,
  대다수 사용자는 어차피 휴지통에 드래그하므로 실효가 없다.

### 3.6 문서화

README에 "완전히 제거하기" 섹션을 둔다. 반드시 포함할 것:

- OS별 제거 절차
- **남는 항목의 정확한 경로**와 각각의 수동 정리 방법
  - 설정·로그 폴더
  - macOS: 키체인 항목, `pkgutil --forget <bundle-id>` (pkg 배포인 경우)
  - Windows: 자격 증명 관리자 항목(훅이 처리하지 않는 경로로 제거했을 때)

## 4. 인수 기준 템플릿

그대로 가져다 쓰고, 해당 없는 항목만 지운다.

**보관소 계층**
1. 저장한 값을 다시 읽으면 같은 값이 나온다.
2. 저장한 적이 없으면 `None`이다.
3. 삭제 후 조회하면 `None`이고, 없는 항목 삭제도 오류가 아니다.
4. 백엔드를 자동 탐색이 아니라 명시 지정한다.
5. 보관소를 못 쓰는 환경에서 앱이 죽지 않고 "미인증" 상태로 떨어진다.
6. 어떤 경로로도 자격증명이 평문 파일로 디스크에 기록되지 않는다.
7. 플랫폼 크기 한도를 넘는 값은 저장 전에 감지해 명확히 실패한다.

**평문 이관**

8. 시작 시 평문 파일이 있으면 보관소로 옮긴다.
9. 이관 후 평문 파일이 실제로 존재하지 않는다.
10. 기록 실패 시 처리가 3.4의 레포별 결정과 일치한다.
11. 평문 파일이 없으면 아무 일도 하지 않는다(멱등).
12. 보관소에 이미 값이 있으면 평문으로 덮어쓰지 않는다.

**제거 훅** (제공되는 플랫폼만)

13. 제거 훅에서 보관소 항목을 삭제한다.
14. 설치·업데이트 훅에서는 삭제하지 않는다.
15. 항목이 없어도 훅은 성공 종료한다.

**문서**

16. README에 OS별 제거 절차와 남는 항목이 문서화된다.

## 5. 알려진 위험

| 위험 | 설명 | 대응 |
|---|---|---|
| ad-hoc 서명과 키체인 ACL | macOS 키체인 항목 접근 권한은 **서명 신원에 묶인다**. ad-hoc 서명은 업데이트로 신원이 바뀔 수 있어 "접근을 허용하시겠습니까" 프롬프트가 반복될 수 있다. | 업데이트 실측으로 확인한다. 반복되면 정식 개발자 인증서 서명이 근본 해결. 사용자가 "허용"을 누르면 동작하므로 기능이 죽지는 않는다. |
| 번들에서 백엔드 탐색 실패 | dist-info 부재로 조용히 빈 백엔드 선택. 개발에서는 통과, 배포본에서만 실패. | 3.2의 명시 지정. 배포본 실측을 인수 기준에 넣는다. |
| Windows blob 한도 | 2560바이트, UTF-16이라 실질 절반. 넘으면 조용히 실패. | 3.3의 사전 검사 + 실측. |
| 헤드리스/CI 환경 | 키체인이 잠겨 있거나 없어 테스트가 실패하거나 멈춘다. | 테스트는 보관소를 가짜 백엔드로 주입해 돌린다. 실제 보관소 접근은 E2E 실측 항목으로 분리한다. |

## 6. 적용 순서 권고

1. **먼저 seam 확인** — `save_*`/`load_*`가 유일한 진입점인지. 아니면 모으는 리팩터링부터.
2. **저장소 계층 교체** (인수 기준 1~7). 테스트는 가짜 백엔드로.
3. **이관 로직** (8~12). 기존 사용자가 있는 상태에서 반드시 먼저 검증한다.
4. **제거 훅** (13~15). Windows 실기 필요.
5. **문서** (16).
6. **배포본 실측** — 번들에서 백엔드가 실제로 잡히는지, 업데이트 후 프롬프트가 뜨는지.
   이 둘은 단위 테스트로 잡히지 않는다.

## 7. 이 레포의 적용 현황

이 레포에서의 구체적인 결정·테스트 케이스·코드 포인터는 R1 검수 문서를 참고한다.
평문 저장 위치는 `src/naver_post_crawler/cookie.py`의 `_COOKIE_FILE`,
교체할 seam은 같은 파일의 `save_cookie()` / `load_cookie()`,
Velopack 훅 패치는 `scripts/flet_template.py`다.
